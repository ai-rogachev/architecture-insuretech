# Описание решений для функциональности ОСАГО

## Архитектурные решения

### 1. Сервис osago-aggregator

#### Хранилище данных
**Решение: Требуется собственное хранилище данных (PostgreSQL)**

**Обоснование:**
- Необходимо хранить состояние заявок на ОСАГО для отслеживания процесса обработки
- Требуется сохранять результаты опроса страховых компаний для последующей обработки
- Нужно хранить метаданные (ID заявок в системах страховых компаний, статусы, временные метки)
- Позволяет обеспечить надежность и возможность восстановления после сбоев
- Изолирует данные от других сервисов, что улучшает масштабируемость

**Структура данных:**
- Таблица заявок (application_id, core_app_request_id, status, created_at)
- Таблица результатов опроса (result_id, application_id, insurance_company_id, offer_data, status, polled_at)
- Таблица метаданных (metadata_id, application_id, insurance_company_id, external_request_id, last_poll_time)

#### API для core-app
**Решение: REST API**

**Эндпоинты:**
- `POST /api/osago/applications` - создание заявки на ОСАГО
  - Принимает данные заявки (информация об автомобиле, клиенте)
  - Возвращает application_id для отслеживания
  - Применяется Rate Limiting для защиты от перегрузки

**Обоснование:**
- REST API прост в реализации и интеграции
- Синхронный запрос на создание заявки позволяет сразу получить ID для отслеживания
- Rate Limiting защищает от перегрузки при пиковых нагрузках (2,5 тысячи одновременных пользователей)

### 2. Интеграция между core-app и osago-aggregator

#### Средство интеграции
**Решение: Гибридный подход - REST + Event-Streaming**

**REST API:**
- Используется для создания заявки (синхронный запрос)
- Применяется Rate Limiting на стороне osago-aggregator

**Event-Streaming (через Message Broker):**
- Используется для передачи предложений от страховых компаний
- osago-aggregator публикует события с предложениями в Kafka
- core-app подписывается на события и получает предложения асинхронно

**Обоснование:**
- Синхронный REST для создания заявки обеспечивает немедленное подтверждение
- Асинхронный Event-Streaming позволяет получать предложения по мере их поступления
- Разделение ответственности: osago-aggregator не блокируется ожиданием всех ответов
- Масштабируемость: несколько экземпляров core-app могут обрабатывать события независимо

### 3. API для веб-приложения в core-app

#### Решение: REST + WebSocket (Server-Sent Events)

**REST API:**
- `POST /api/osago/requests` - создание заявки на ОСАГО
  - Принимает данные заявки от пользователя
  - Возвращает request_id и WebSocket endpoint для подключения

**WebSocket API:**
- `WS /api/osago/stream/{request_id}` - поток предложений в реальном времени
  - Подключение устанавливается после создания заявки
  - Сервер отправляет предложения по мере их поступления от страховых компаний
  - Каждое предложение содержит: ID страховой компании, условия, цену, статус

**Обоснование:**
- REST для создания заявки - стандартный подход, прост в реализации
- WebSocket/SSE для получения предложений в реальном времени соответствует требованию "отображать предложения сразу, как только пришёл ответ"
- Позволяет обновлять UI без polling, что снижает нагрузку на сервер
- Улучшает пользовательский опыт - пользователь видит предложения по мере их поступления

**Учет множественных экземпляров:**
- Используется sticky session (session affinity) для WebSocket соединений
- Альтернатива: shared state через Redis для маршрутизации событий к правильному экземпляру
- События из Message Broker распределяются между экземплярами core-app, каждый экземпляр отправляет события только своим подключенным клиентам

### 4. Интеграция между веб-приложением и core-app

#### Средство интеграции
**Решение: REST + WebSocket (Server-Sent Events)**

**REST:**
- Используется для всех стандартных операций (создание заявки, получение данных)
- Применяется Rate Limiting для защиты от злоупотреблений

**WebSocket/SSE:**
- Используется для получения предложений ОСАГО в реальном времени
- Односторонняя связь от сервера к клиенту (Server-Sent Events)
- Автоматическое переподключение при разрыве соединения

**Обоснование:**
- WebSocket/SSE обеспечивает низкую задержку доставки предложений
- Соответствует требованию бизнеса о немедленном отображении предложений
- Снижает нагрузку на сервер по сравнению с polling
- Улучшает пользовательский опыт

### 5. Паттерны отказоустойчивости

#### Circuit Breaker
**Применение:** В osago-aggregator при взаимодействии со страховыми компаниями

**Обоснование:**
- Защищает от каскадных сбоев при недоступности страховых компаний
- При превышении порога ошибок разрывает цепь и не отправляет запросы
- Позволяет системе продолжать работу даже если некоторые страховые компании недоступны
- Уменьшает нагрузку на проблемные сервисы

**Настройки:**
- Порог ошибок: 50% за последние 10 запросов
- Время ожидания перед повторной попыткой: 30 секунд
- Timeout для каждого запроса: 60 секунд (максимальное время ожидания решения)

#### Retry
**Применение:** В osago-aggregator при опросе решений от страховых компаний

**Обоснование:**
- Страховые компании могут обрабатывать заявки асинхронно
- Необходимо периодически опрашивать статус заявки
- Retry с экспоненциальной задержкой позволяет эффективно получать результаты

**Настройки:**
- Максимальное количество попыток: 20 (в течение 60 секунд)
- Интервал между попытками: экспоненциальная задержка (1s, 2s, 4s, 8s...)
- Максимальное время ожидания: 60 секунд (требование бизнеса)

#### Timeout
**Применение:** 
- В osago-aggregator при запросах к страховым компаниям: 60 секунд
- В core-app при запросах к osago-aggregator: 5 секунд (создание заявки)
- В веб-приложении при WebSocket соединении: без таймаута (долгоживущее соединение)

**Обоснование:**
- 60 секунд - максимальное время ожидания решения от страховой компании (требование бизнеса)
- 5 секунд для создания заявки - достаточно для синхронной операции
- WebSocket без таймаута - соединение должно оставаться открытым для получения предложений

#### Rate Limiting
**Применение:**
- На входе в osago-aggregator (REST API от core-app)
- На входе в core-app (REST API от веб-приложения)

**Обоснование:**
- Защита от перегрузки при пиковых нагрузках (2,5 тысячи одновременных пользователей)
- Предотвращение злоупотреблений и DDoS атак
- Обеспечение справедливого распределения ресурсов

**Настройки:**
- osago-aggregator: 1000 запросов в минуту на экземпляр
- core-app: 100 запросов в минуту на пользователя (по IP или session)

### 6. Учет множественных экземпляров сервисов

#### Проблемы и решения

**Проблема 1: WebSocket соединения**
- При множественных экземплярах core-app WebSocket соединение может быть установлено с одним экземпляром, а события приходят в другой

**Решение:**
- Использование sticky session (session affinity) на уровне load balancer
- Альтернатива: shared state через Redis для маршрутизации событий к правильному экземпляру
- Каждый экземпляр core-app отслеживает свои активные WebSocket соединения

**Проблема 2: Обработка событий из Message Broker**
- События из Kafka должны обрабатываться только один раз, но могут обрабатываться несколькими экземплярами

**Решение:**
- Использование consumer groups в Kafka
- Каждое событие обрабатывается только одним экземпляром в группе
- Идемпотентность обработки событий (проверка дубликатов)

**Проблема 3: Состояние заявок в osago-aggregator**
- При множественных экземплярах osago-aggregator необходимо обеспечить консистентность данных

**Решение:**
- Использование общей БД (PostgreSQL) для всех экземпляров
- Транзакции и блокировки для обеспечения консистентности
- Оптимистичные блокировки для предотвращения конфликтов

**Проблема 4: Распределение нагрузки при запросах к страховым компаниям**
- При множественных экземплярах osago-aggregator необходимо равномерно распределить нагрузку

**Решение:**
- Каждый экземпляр osago-aggregator обрабатывает свои заявки независимо
- Балансировка нагрузки на уровне core-app при вызове osago-aggregator
- Circuit Breaker на уровне каждого экземпляра для изоляции проблем

## Схема потока данных

1. **Пользователь создает заявку:**
   - Веб-приложение → REST → core-app (Rate Limiting)
   - core-app → REST → osago-aggregator (Rate Limiting)
   - osago-aggregator сохраняет заявку в БД
   - osago-aggregator отправляет запросы во все страховые компании (Circuit Breaker, Retry, Timeout: 60s)

2. **Получение предложений:**
   - Страховые компании обрабатывают заявки асинхронно
   - osago-aggregator опрашивает решения (Retry с экспоненциальной задержкой)
   - При получении предложения osago-aggregator публикует событие в Kafka
   - core-app получает событие из Kafka
   - core-app отправляет предложение клиенту через WebSocket

3. **Отображение предложений:**
   - Веб-приложение получает предложения через WebSocket в реальном времени
   - Предложения отображаются сразу по мере поступления
   - Процесс завершается через 60 секунд или когда получены все предложения

## Преимущества решения

1. **Масштабируемость:** Асинхронная обработка позволяет справляться с пиковыми нагрузками
2. **Надежность:** Паттерны отказоустойчивости защищают от сбоев
3. **Производительность:** WebSocket обеспечивает низкую задержку доставки предложений
4. **Устойчивость:** Circuit Breaker изолирует проблемы с отдельными страховыми компаниями
5. **Пользовательский опыт:** Предложения отображаются сразу по мере поступления
6. **Гибкость:** Множественные экземпляры обеспечивают высокую доступность

# Описание архитектурных решений для InsureTech

## Требования бизнеса

- **Развитие в регионах РФ** - необходимо обслуживать клиентов из всех часовых поясов
- **RTO (Recovery Time Objective)**: 45 минут
- **RPO (Recovery Point Objective)**: 15 минут
- **Доступность**: 99.9% (8.76 часов простоя в год)
- **Одинаковое время загрузки** для пользователей из разных регионов
- **Объем данных**: 50 GB

## 1. Стратегия масштабирования и отказоустойчивости

### Горизонтальное масштабирование
**Выбрано:** Горизонтальное масштабирование

**Обоснование:**
- Позволяет масштабировать систему по мере роста нагрузки
- Легко добавлять новые инстансы в Kubernetes
- Автоматическое масштабирование на основе метрик (HPA)
- Более экономично, чем вертикальное масштабирование

### Вертикальное масштабирование
**Не выбрано** как основная стратегия, но может использоваться для оптимизации отдельных компонентов

### Использование дополнительных зон безопасности
**Выбрано:** 3 зоны доступности в разных географических регионах

**Зоны:**
1. **Москва (ru-central1-a)** - основная зона
2. **Санкт-Петербург (ru-central1-b)** - резервная зона
3. **Екатеринбург (ru-central1-c)** - резервная зона

**Обоснование:**
- Географическое распределение обеспечивает отказоустойчивость
- Снижение задержки для пользователей из разных регионов
- Соответствие требованиям 99.9% доступности
- Изоляция отказов - сбой в одной зоне не влияет на другие

## 2. Конфигурация развёртывания в Kubernetes

### Решение: Независимые кластеры в каждой зоне

**Обоснование:**

1. **Изоляция отказов**
   - Сбой одного кластера не влияет на другие
   - Независимое управление жизненным циклом

2. **Независимое масштабирование**
   - Каждая зона масштабируется независимо в зависимости от нагрузки
   - Оптимизация ресурсов под региональную нагрузку

3. **Соответствие требованиям RTO 45 мин**
   - Быстрое переключение между зонами
   - Готовые реплики приложений в каждой зоне

4. **Простота управления**
   - Каждый кластер управляется независимо
   - Упрощенное развертывание и обновление

5. **Соответствие требованиям безопасности**
   - Изоляция данных по регионам
   - Соответствие требованиям локализации данных

**Альтернатива (растянутый кластер) отклонена:**
- Высокая задержка между нодами в разных зонах
- Сложность управления сетью
- Риск split-brain при разделении сети

## 3. Балансировка нагрузки

### Многоуровневая балансировка

#### Уровень 1: Global Load Balancer
**Технология:** Yandex Application Load Balancer

**Функции:**
- Геолокационная маршрутизация - направление трафика в ближайшую зону
- DNS-based routing для оптимальной маршрутизации
- Health Check на уровне зон

**Health Check:**
- Протокол: HTTP
- Endpoint: `/health`
- Interval: 10 секунд
- Timeout: 5 секунд
- Unhealthy threshold: 2 последовательных неудачных проверки

#### Уровень 2: Regional Load Balancer
**Технология:** Yandex Application Load Balancer (в каждой зоне)

**Функции:**
- Распределение нагрузки между подами в кластере
- Health Check на уровне подов
- Автоматическое исключение нездоровых подов

**Health Check:**
- Протокол: HTTP
- Endpoint: `/health`
- Interval: 5 секунд
- Timeout: 3 секунды
- Unhealthy threshold: 2 последовательных неудачных проверки

#### Уровень 3: Kubernetes Service
**Технология:** Kubernetes Service (ClusterIP/LoadBalancer)

**Функции:**
- Внутренняя балансировка в кластере
- Service discovery
- Health Check через readiness и liveness probes

**Health Check:**
- Readiness probe: проверка готовности пода принимать трафик
- Liveness probe: проверка работоспособности пода

### Стратегия маршрутизации

1. **Геолокационная маршрутизация**
   - Пользователи из Москвы → Зона 1
   - Пользователи из Санкт-Петербурга → Зона 2
   - Пользователи из Екатеринбурга → Зона 3
   - Остальные регионы → ближайшая зона

2. **Failover маршрутизация**
   - При недоступности ближайшей зоны → переключение на резервную
   - Автоматическое переключение через DNS

3. **Балансировка внутри зоны**
   - Round-robin между подами
   - Учет загрузки подов

## 4. Фейловер-стратегия

### Многоуровневая стратегия отказоустойчивости

#### Уровень приложения

**Автоматическое переключение между зонами:**
- При недоступности зоны Global LB автоматически переключает трафик на ближайшую зону доступа
- Время переключения: 30-60 секунд (время обнаружения + DNS TTL)
- Health Check на всех уровнях обеспечивает быстрое обнаружение проблем

**Стратегия:**
1. Health Check обнаруживает недоступность зоны
2. Global LB исключает зону из маршрутизации
3. Трафик перенаправляется в резервные зоны
4. DNS обновляется (TTL 60 секунд)

#### Уровень базы данных

**Автоматический failover БД:**
- Использование Yandex Managed PostgreSQL с автоматическим failover
- Синхронная репликация в зоне 1 обеспечивает RPO 15 мин
- Асинхронная репликация в зоны 2 и 3 для географического распределения

**Сценарии failover:**

1. **Отказ Master в зоне 1:**
   - Автоматическое переключение на синхронную реплику в зоне 1
   - Время переключения: < 5 минут
   - RPO: 0 (синхронная репликация)

2. **Отказ всей зоны 1:**
   - Переключение на асинхронную реплику в зоне 2 или 3
   - Время переключения: < 15 минут
   - RPO: до 15 минут (время последнего снимка)

3. **Частичный отказ:**
   - Переключение на резервную зону на уровне приложения
   - БД продолжает работать в основной зоне

### Обеспечение требований RTO и RPO

**RTO 45 минут:**
- Автоматический failover на уровне приложения: 30-60 сек
- Автоматический failover БД: < 15 минут
- Резервные зоны готовы к работе
- **Итого: RTO < 45 минут ✓**

**RPO 15 минут:**
- Синхронная репликация в зоне 1: RPO = 0
- Автоматические снимки каждые 15 минут
- Асинхронная репликация в другие зоны: RPO до 15 минут
- **Итого: RPO ≤ 15 минут ✓**

## 5. Конфигурация базы данных

### Архитектура БД

**Технология:** Yandex Managed PostgreSQL

**Конфигурация:**

1. **Master (Зона 1 - Москва)**
   - Primary instance
   - Обработка всех запросов на запись
   - Синхронная репликация в зоне 1

2. **Синхронная реплика (Зона 1 - Москва)**
   - Hot standby для быстрого failover
   - Синхронная репликация обеспечивает RPO = 0
   - Готова к переключению за < 5 минут

3. **Асинхронные реплики (Зоны 2 и 3)**
   - Географическое распределение данных
   - Standby для failover при отказе зоны 1
   - RPO до 15 минут

### Резервное копирование

**Стратегия:**

1. **Автоматические снимки**
   - Частота: каждые 15 минут
   - Хранение: Yandex Object Storage
   - Срок хранения: 30 дней
   - Обеспечивает RPO 15 минут

2. **Ежедневные полные бэкапы**
   - Время: 02:00 МСК (вне пиковых нагрузок)
   - Хранение: Yandex Object Storage
   - Срок хранения: 90 дней

3. **Еженедельные бэкапы**
   - Хранение: Yandex Object Storage
   - Срок хранения: 1 год

4. **Тестирование восстановления**
   - Ежемесячное тестирование восстановления из бэкапа
   - Проверка соответствия RTO 45 минут

### Фреймворк конфигурации кластера БД

**Yandex Managed PostgreSQL:**
- Автоматическое управление репликацией
- Автоматический failover
- Мониторинг и алертинг
- Автоматические обновления и патчи
- Управление бэкапами

## 6. Шардирование базы данных

### Решение: Шардирование НЕ требуется

**Обоснование:**

1. **Объем данных: 50 GB**
   - Небольшой объем, легко помещается в одну БД
   - PostgreSQL может эффективно работать с таким объемом

2. **Сложность шардирования**
   - Увеличивает сложность архитектуры
   - Требует дополнительных ресурсов на управление
   - Усложняет запросы, пересекающие шарды

3. **Текущая нагрузка**
   - При росте нагрузки сначала используем горизонтальное масштабирование приложений
   - Реплики БД для чтения снижают нагрузку на Master

4. **Будущее масштабирование**
   - При росте объема данных до 500+ GB можно рассмотреть шардирование
   - Сейчас это преждевременно

**Альтернатива:** Если в будущем потребуется шардирование, можно использовать:
- PostgreSQL с расширением Citus
- Или горизонтальное разделение по регионам (географическое шардирование)

## 7. CDN для статики

### Технология: Yandex CDN

**Функции:**
- Кэширование статических ресурсов (JS, CSS, изображения)
- Географически распределенные точки присутствия
- Снижение задержки для пользователей из разных регионов
- Одинаковое время загрузки независимо от географического положения

**Конфигурация:**
- Кэширование статики на 24 часа
- Автоматическая инвалидация при обновлении
- HTTPS поддержка
- Сжатие (gzip, brotli)

## 8. Обеспечение одинакового времени загрузки

### Стратегия:

1. **Геолокационная маршрутизация**
   - Пользователи направляются в ближайшую зону
   - Минимизация задержки сети

2. **CDN для статики**
   - Статические ресурсы кэшируются в точках присутствия
   - Быстрая загрузка независимо от расположения

3. **Оптимизация приложения**
   - Минимизация количества запросов
   - Использование HTTP/2
   - Сжатие данных

4. **Мониторинг производительности**
   - Отслеживание времени загрузки из разных регионов
   - Алертинг при превышении порогов

## Итоговая архитектура

### Компоненты:

1. **3 зоны доступности** в разных географических регионах
2. **3 независимых Kubernetes кластера** (по одному в каждой зоне)
3. **Многоуровневая балансировка нагрузки** (Global LB + Regional LB)
4. **PostgreSQL с репликацией** (Master + 3 реплики)
5. **Автоматическое резервное копирование** (каждые 15 минут)
6. **CDN для статики** (Yandex CDN)
7. **Health Check на всех уровнях**

### Соответствие требованиям:

- ✅ **RTO 45 мин**: Автоматический failover обеспечивает переключение < 45 минут
- ✅ **RPO 15 мин**: Синхронная репликация + снимки каждые 15 минут
- ✅ **Доступность 99.9%**: Множественные зоны + автоматический failover
- ✅ **Одинаковое время загрузки**: CDN + геолокационная маршрутизация
- ✅ **24/7 работа**: Распределение по часовым поясам
- ✅ **Масштабируемость**: Горизонтальное масштабирование в Kubernetes

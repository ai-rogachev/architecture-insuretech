# Анализ проблем и рисков архитектуры InsureTech

## Текущая архитектура

### Описание текущих взаимодействий:
1. **ins-product-aggregator** синхронно запрашивает информацию из всех страховых компаний (сейчас 5) в рамках одного REST-запроса
2. **core-app** запрашивает ins-product-aggregator каждые 15 минут для обновления локальной реплики данных о продуктах
3. **ins-comp-settlement** запрашивает ins-product-aggregator раз в сутки (ночью) для получения данных о продуктах и тарифах
4. **ins-comp-settlement** запрашивает core-app раз в сутки по REST API для получения всех оформленных за день страховок

## Проблемы и риски при росте нагрузки

### 1. Проблемы масштабируемости ins-product-aggregator

**Проблема:** При увеличении количества страховых компаний с 5 до 10, синхронный запрос ко всем компаниям в рамках одного HTTP-запроса приведет к:
- **Увеличению времени ответа в 2 раза** (при линейном росте) или более (при нелинейных задержках)
- **Риску таймаутов** - если хотя бы одна компания отвечает медленно, весь запрос может завершиться ошибкой
- **Каскадным сбоям** - ошибка одной страховой компании может привести к недоступности всего списка продуктов
- **Высокой нагрузке на сеть** - одновременные запросы ко всем компаниям создают пиковые нагрузки

**Риск:** При 10 компаниях время ответа может превысить допустимые таймауты (обычно 30-60 секунд), что приведет к ошибкам в пользовательских запросах.

### 2. Проблемы синхронного polling в core-app

**Проблема:** Запросы core-app к ins-product-aggregator каждые 15 минут создают:
- **Постоянную нагрузку** на ins-product-aggregator, даже когда данные не изменились
- **Неэффективное использование ресурсов** - большинство запросов возвращают те же данные
- **Риск race conditions** - если запрос выполняется дольше 15 минут, может возникнуть ситуация с параллельными запросами
- **Проблемы с актуальностью данных** - данные могут быть устаревшими до 15 минут

**Риск:** При росте количества компаний до 10, запросы могут начать занимать больше 15 минут, что приведет к наложению запросов и перегрузке системы.

### 3. Проблемы синхронного polling в ins-comp-settlement

**Проблема:** Ежедневный запрос ins-comp-settlement к ins-product-aggregator:
- **Создает пиковую нагрузку** в ночное время, когда выполняется формирование реестра
- **Блокирует процесс формирования реестра** - если запрос к ins-product-aggregator затягивается, весь процесс задерживается
- **Риск сбоя всего процесса** - при ошибке ins-product-aggregator реестр не может быть сформирован

**Риск:** При росте до 10 компаний ночной запрос может занять слишком много времени, что нарушит SLA формирования реестра.

### 4. Проблемы синхронного запроса ins-comp-settlement к core-app

**Проблема:** Ежедневный REST-запрос ins-comp-settlement к core-app для получения оформленных страховок:
- **Создает сильную связанность** между сервисами - core-app должен быть доступен в момент формирования реестра
- **Риск потери данных** - если core-app недоступен в момент запроса, данные за день могут быть потеряны
- **Проблемы с производительностью** - при большом количестве оформленных страховок запрос может быть очень тяжелым
- **Отсутствие гарантии доставки** - нет механизма повторной попытки при сбое

**Риск:** При росте бизнеса количество оформленных страховок может вырасти, что сделает запрос очень медленным или приведет к таймауту.

### 5. Проблемы с локальными репликами данных

**Проблема:** Локальные реплики данных в core-app и ins-comp-settlement:
- **Могут быть неактуальными** - максимальная задержка до 15 минут для core-app и до 24 часов для ins-comp-settlement
- **Дублирование данных** - одни и те же данные хранятся в нескольких местах
- **Проблемы с консистентностью** - разные сервисы могут иметь разные версии данных
- **Увеличение нагрузки на БД** - необходимо хранить и обновлять реплики

**Риск:** Неактуальные данные могут привести к бизнес-ошибкам (например, показать клиенту неактуальный тариф).

### 6. Проблемы с обработкой ошибок внешних API

**Проблема:** Ошибки при взаимодействии с API страховых компаний:
- **Влияют на весь процесс** - ошибка одной компании может заблокировать получение данных от всех остальных
- **Отсутствие механизма retry** - нет автоматических повторных попыток
- **Нет изоляции ошибок** - проблема с одной компанией влияет на работу со всеми

**Риск:** При росте до 10 компаний вероятность ошибок хотя бы одной компании увеличивается, что может привести к частым сбоям.

### 7. Проблемы с производительностью при росте нагрузки

**Проблема:** При удвоении количества страховых компаний:
- **Увеличится время обработки запросов** в ins-product-aggregator
- **Возрастет нагрузка на сеть** - больше одновременных соединений
- **Увеличится потребление памяти** - больше данных для агрегации
- **Возрастет нагрузка на БД** - больше записей для хранения

**Риск:** Система может не справиться с нагрузкой, что приведет к деградации производительности или полному отказу.

## Резюме критических рисков

1. **Высокий риск:** Синхронные запросы ко всем страховым компаниям приведут к таймаутам и ошибкам
2. **Высокий риск:** Polling каждые 15 минут станет неэффективным и может создать перегрузку
3. **Средний риск:** Ежедневные синхронные запросы для формирования реестра могут нарушить SLA
4. **Средний риск:** Неактуальность данных в локальных репликах может привести к бизнес-ошибкам
5. **Средний риск:** Отсутствие изоляции ошибок приведет к каскадным сбоям

## Рекомендации по решению

1. **Переход на Event-Streaming** для асинхронной передачи данных о продуктах и тарифах
2. **Использование паттерна Transactional Outbox** для надежной доставки событий о новых страховках
3. **Внедрение Message Broker** (Kafka/RabbitMQ) для асинхронной коммуникации
4. **Реализация механизма retry и circuit breaker** для работы с внешними API
5. **Использование event-driven обновлений** вместо polling для актуализации данных
